# 多智能体狼人杀 Team 系统

## 项目内容总结

该项目的核心目标是**构建一个基于大语言模型（LLM）的、具备高度自主决策与博弈对抗能力的多智能体狼人杀 Team 系统**。

### 一、核心架构设计

**多智能体协作/对抗框架**：利用现有的多Agent框架（LangGraph）构建玩家生态。每个Agent代表一个独立的玩家，具备高水平的文本理解和长文本生成能力

**信息隔离与认知：**系统必须在底座上实现严格的权限控制，按照下面狼人杀游戏规则

**胜利条件**

游戏分为两个互相对立的阵营，采用**屠边规则**：

| 阵营         | 包含身份                 | 胜利条件                                                     |
| ------------ | ------------------------ | ------------------------------------------------------------ |
| **好人阵营** | 预言家、女巫、猎人、村民 | **消灭所有狼人**。                                           |
| **狼人阵营** | 基础狼人                 | **屠边成功**：即所有【神职】全部死亡，或所有【平民】全部死亡。 |

**游戏流程**

法官（Game Master）将通过以下严格的状态机驱动游戏：

```
天黑闭眼 ──► 狼人密聊刀人 ──► 预言家验人 ──► 女巫用药判定 ──► 天亮了
                                                                 │
                                                                 ▼
公放逐投 ◄── 自由发言辩论 ◄── 竞选警长(上警) ◄── 法官宣布死讯 ◄── 结算夜间伤亡

```

1. **警长竞选（首日白天）**：玩家可选择“上警”争夺警徽。参选玩家轮流发言，由未参选（警下）的 Agent 投票选出警长。警长拥有 **1.5 票**投票权并可决定发言顺序。
2. **白天发言与公投**：法官宣布死讯（死者留遗言）幸存 Agent 依次进行文本发言（大模型需完成：**表水**自证、**踩**他人漏洞、或**悍跳**伪装）所有人公开投票放逐一名嫌疑人（得票最高者出局并留遗言）。
3. **循环直至终局**：重复黑夜与白天，直到触发引擎的胜负判定条件，宣告游戏结束。

**职责划分**

| 阵营 | 角色     | 人数 | Agent开发要点                                                |
| ---- | -------- | ---- | ------------------------------------------------------------ |
| 狼人 | 普通狼人 | 2    | 团队协作，需实现团队共识机制，内部私信机制；若意见不合需有兜底策略（如强制空刀或随机） |
| 神职 | 预言家   | 1    | 验人信息占比极高（6人中验1人=16.7%覆盖率），Prompt需强调信息的珍贵性 |
|      | 女巫     | 1    | 建议仅保留解药，去掉毒药。6人局毒药过于致命，容易导致好人瞬间崩盘 |
| 平民 | 平民     | 2    | 样本太少，推理难度极大。需在Prompt中注入更多"表水"和"站边"逻辑模板 |

**1. 狼人阵营 (Werewolves)**

| 角色         | 核心职责                                                     | 已知信息 (Private)                         | 未知信息 (Blind)                                           | Agent 开发关键点                                             |
| :----------- | :----------------------------------------------------------- | :----------------------------------------- | :--------------------------------------------------------- | :----------------------------------------------------------- |
| **普通狼人** | 夜间参与击杀投票；白天伪装好人/悍跳神职；团队配合冲票或倒钩。 | 队友编号；每晚击杀目标；己方战术沟通内容。 | 所有神职身份；所有平民身份；预言家验人结果；女巫用药情况。 | 需实现**团队共识机制**；Prompt需包含"欺骗策略"和"角色扮演"指令。 |

**2. 神职阵营 (Gods)**

| 角色       | 核心职责                                                     | 已知信息 (Private)                     | 未知信息 (Blind)                                           | Agent 开发关键点                                             |
| :--------- | :----------------------------------------------------------- | :------------------------------------- | :--------------------------------------------------------- | :----------------------------------------------------------- |
| **预言家** | 每晚查验1名玩家身份（金水/查杀）；白天报验人信息，争取警徽。 | 自己查验过的玩家结果（累积记忆）。     | 未查验玩家的身份；其他神职是谁；狼人具体是谁（除非验到）。 | **记忆模块是核心**：必须维护一个`VerifiedList`，防止遗忘或篡改历史验人结果。 |
| **女巫**   | 拥有一瓶解药（救被刀者）和一瓶毒药（毒杀一人），全程各限一次。 | 每晚被刀的玩家编号；自身双药使用状态。 | 被刀者的真实身份；狼人是谁；预言家验人结果。               | 需实现**资源状态锁**（`hasAntidote`, `hasPoison`）；首夜自救规则需可配置。 |

**3. 平民阵营 (Villagers)**

| 角色     | 核心职责                                 | 已知信息 (Private)           | 未知信息 (Blind)                           | Agent 开发关键点                                             |
| :------- | :--------------------------------------- | :--------------------------- | :----------------------------------------- | :----------------------------------------------------------- |
| **平民** | 白天通过发言和投票找出狼人；无夜间技能。 | **仅知道自己的身份是平民**。 | **一切**：谁是狼、谁是神、昨晚发生了什么。 | 最考验推理能力的角色；Prompt应强调"逻辑分析"而非"信息陈述"；需防止平民Agent瞎编信息。 |

### **二、 信息隔离的技术实现架构**

在代码层面，绝不能将所有信息塞给同一个LLM上下文。推荐采用 **"中央裁判 + 私有信道"** 架构：

```
graph TD
    GM[Game Master / 裁判系统] -->|公开广播| PublicChannel[公共频道: 发言/投票/死讯]
    GM -->|私有消息| WolfChannel[狼人私有频道: 队友/击杀]
    GM -->|私有消息| SeerChannel[预言家私有频道: 验人结果]
    GM -->|私有消息| WitchChannel[女巫私有频道: 被刀者/药效]

	PublicChannel --> AllAgents[所有Agent]
	WolfChannel --> WolfAgents[仅狼人Agent]
	SeerChannel --> SeerAgent[仅预言家Agent]
	WitchChannel --> WitchAgent[仅女巫Agent]
```

**全程可观测性日志（Structured Logging）**：系统会实时输出结构化日志，不仅记录“谁死了”、“谁投了谁”，更重要的是捕获 Agent 的**内心独白（Thought/Chain-of-Thought）**、发言草稿以及策略修正过程。

### 三、技术选型

| 组件      | 技术选型      | 选型理由                                                    |
| --------- | ------------- | ----------------------------------------------------------- |
| Web框架   | FastAPI       | 原生async/await，适合Agent异步推理；Pydantic V2校验消息格式 |
| Agent编排 | LangGraph     | 内置状态机和消息路由，避免手写复杂的if-else流转             |
| 实时通信  | WebSocket     | 狼人杀是强实时交互，HTTP轮询延迟高且浪费资源                |
| 数据存储  | SQLite        | 发无需装数据库，单文件存储对局记录和Agent记忆               |
| LLM调用   | LiteLLM       | 统一封装OpenAI LLM接口                                      |
| 任务队列  | asyncio.Queue | 本地单机无需redis/mq                                        |

##### ** 接口架构设计原则**

>  **核心设计理念：Server-Authoritative（服务端权威）**
> AI Agent **绝不直接互相调用接口**。所有Agent只与FastAPI后端通信，由后端充当"裁判（Game Master）"负责信息过滤、规则校验和消息分发。这从根本上杜绝了信息泄露和规则作

####  2.**RESTful API 设计（游戏生命周期管理）**

仅用于游戏的创建、配置和元数据查询，**不参与回合内实时交互**。

```http
# 1. 创建对局（传入板子配置）
POST /api/v1/games
Body: {
  "board_type": "6_standard",      # 预设板子或自定义
  "roles": {"werewolf":2, "seer":1, "witch":1, "villager":2},
  "win_condition": "all_kill",     # 屠城制
  "llm_model": "qwen3-8b"
}
Response: {"game_id": "g_abc123", "status": "created"}

# 2. 获取当前游戏状态（仅返回该请求者可见的公开信息）
GET /api/v1/games/{game_id}/state
Response: {
  "phase": "day_discuss",
  "round": 2,
  "alive_players": [1,2,4,5,6],
  "public_log": ["[系统] 昨晚平安夜", "[3号] 我是预言家..."]
}

# 3. 获取对局回放/日志（调试用）
GET /api/v1/games/{game_id}/replay
```

#### 3.游戏阶段说明

每调用一次 `step`，游戏推进一个内部阶段。阶段按以下顺序循环：

| 索引 | 阶段标识       | 说明                            |
| ---- | -------------- | ------------------------------- |
| 0    | `night_wolf`   | 狼人投票选择击杀目标            |
| 1    | `night_seer`   | 预言家查验一名玩家              |
| 2    | `night_witch`  | 女巫决定是否用药                |
| 3    | `night_result` | 宣布夜晚死亡结果 + 猎人开枪结算 |
| 4    | `day_start`    | 白天开始，公布昨晚信息          |
| 5    | `speech`       | 所有存活玩家依次发言            |
| 6    | `vote`         | 全体投票放逐                    |
| 7    | `day_end`      | 检查胜负 → 天数 +1 或 游戏结束  |

`step` 响应示例：

```json
{
  "phase": "night_wolf",
  "day_number": 1,
  "step_data": {
    "wolf_votes": [{"player_id": 0, "target": 3}],
    "final_target": 3
  },
  "players": [
    {"player_id": 0, "name": "玩家1", "role": "werewolf", "is_alive": true, ...},
    ...
  ],
  "dialogues": [],
  "deaths": [],
  "is_game_over": false,
  "winner": null
}
```

当 `is_game_over` 为 `true` 时，`winner` 字段会返回胜利方（`"good"` 或 `"evil"`），后续 `step` 调用将始终返回 `game_over` 状态。

#### 4.创建请求参数

| 参数            | 类型         | 默认值       | 说明                                           |
| --------------- | ------------ | ------------ | ---------------------------------------------- |
| `config_name`   | string       | `standard_6` | 角色配置名：`standard_6`、`simple_4`、`big_9`  |
| `player_names`  | list[string] | null         | 自定义玩家名称，不传则自动生成                 |
| `shuffle`       | bool         | true         | 是否随机打乱角色分配                           |
| `player_styles` | dict         | null         | 玩家决策风格，`{"0": "bold", "1": "cautious"}` |

可用决策风格：`balanced`（平衡）、`bold`（大胆）、`cautious`（谨慎）、`random`（随机）。

#### **5.WebSocket 接口设计（核心实时交互）**

这是整个系统的血脉。每个Agent（及观战前端）建立一个WS连接。

##### **连接端点**

```
ws://localhost:8000/ws/{game_id}/{player_id}?token=xxx
```

##### **消息协议规范（JSON）**

所有消息必须包含 `type` 字段，采用 **Pydantic Discriminated Union** 严格校验：

##### **① Server → Client（下行消息）**

| type               | 触发时机      | payload 示例                                                 | 信息隔离说明                                    |
| :----------------- | :------------ | :----------------------------------------------------------- | :---------------------------------------------- |
| `game_start`       | 游戏开始      | `{"role":"werewolf","teammates":[2],"seat":1}`               | **仅本人可见自己的role**，狼人额外收到teammates |
| `phase_change`     | 阶段切换      | `{"phase":"night_wolf","timeout_sec":30}`                    | 所有人收到，但只有狼人可在此阶段行动            |
| `private_info`     | 私密信息推送  | `{"info_type":"verify_result","target":4,"is_werewolf":false}` | **仅预言家收到**，其他人完全无此消息            |
| `public_broadcast` | 公开事件      | `{"event":"player_speak","seat":3,"content":"..."}`          | 所有人收到                                      |
| `action_request`   | 要求Agent决策 | `{"valid_actions":["kill_1","kill_3","skip"],"deadline":...}` | 仅当前行动角色收到                              |
| `game_over`        | 游戏结束      | `{"winner":"werewolf","reason":"all_gods_dead"}`             | 所有人收到                                      |

**② Client → Server（上行消息）**

| type            | 触发时机           | payload 示例                   | 服务端校验                                   |
| :-------------- | :----------------- | :----------------------------- | :------------------------------------------- |
| `ready`         | 收到game_start后   | `{}`                           | 全员ready后才进入第一阶段                    |
| `action`        | 响应action_request | `{"action":"kill","target":4}` | 校验：是否存活、目标是否合法、是否在正确阶段 |
| `speak`         | 白天发言阶段       | `{"content":"我觉得3号像狼"}`  | 校验：是否轮到该玩家发言、内容长度限制       |
| `self_destruct` | 狼人自爆           | `{}`                           | 校验：是否为狼人、是否在白天发言阶段         |

#### 6. **针对AI Agent的特殊优化**

1. **超时兜底机制：** LLM可能卡死或拒绝输出。`action_request` 必须带 `deadline`，超时后GM自动执行默认动作（狼人空刀、神职跳过、平民弃票），**绝不能阻塞整局游戏**。
2. **结构化输出强制：** 在System Prompt中明确要求Agent以JSON回复，并在WS服务端做二次解析。若解析失败，给予一次重试机会，仍失败则走兜底。
3. **Token限流：** 本地跑多个Agent容易打满GPU/上下文。建议在GM层加一个 `asyncio.Semaphore(2)`，限制同时推理的Agent数量，避免OOM。
4. **热重载支持：** 开发期间Agent Prompt会频繁调整。将Prompt模板外置为YAML/Jinja2文件，通过 `/api/v1/config/reload` 接口热更新，无需重启服务重开对局。

#### **必备功能模块（按优先级排序）**

1. **全局状态栏：** 当前阶段、轮次、存活状态、倒计时（最高优先级）
2. **分角色视角切换器：** 下拉框切换"上帝视角/1号玩家/2号玩家..."，实时展示该视角下的可见信息（验证信息隔离是否正确）
3. **结构化日志流：** 区分系统消息、公开发言、私密行动，支持按角色/类型过滤
4. **Agent 决策快照：** 点击某条发言/投票，弹出该次决策的原始 Prompt 和 LLM 返回内容（调试核心）
5. **关系图谱（进阶）：** 动态展示"谁投了谁""谁验了谁""谁救了谁"，辅助分析 Agent 策略
